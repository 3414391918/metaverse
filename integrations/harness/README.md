# Harness integration

The app ships `@deepseek-ai/dsh@0.2.1-rc.2` from `apps/harness`. It does not require a sibling Harness checkout, global Node.js, or global pnpm. `tools/build-harness.mjs` stages its production dependencies and the integration plugin. The packaging hook stages the matching OS/architecture; the complete runtime is unpacked from ASAR for native modules and child processes.

The assistant starts lazily through the supported `runCli` API and named `web` profile. The child uses a bundled Node 24.19.0 executable, bundled pnpm and a local Node shim for plugin installation. Harness's module interceptor does not support Electron 42's embedded Node, so the core runs independently of Electron. The backend binds to an authenticated random loopback port. App exit, restart, and working directory changes stop the owned child. Switching away from the assistant page leaves active tasks running.

Persistent state is `<work-directory>/assistant`: profiles, credentials, sessions, attachments and workspace records. Keeping it outside the regenerable `.metaverse` index lets the normal workspace data migration include it. Generated overlay, platform guide and Node shim are replaced at launch. Existing conversations retain Harness's recorded working directory; changing a session's workspace follows Harness's workspace controls. Switching directories isolates the full assistant home. Recovering a directory reopens its original assistant state.

The guest webview uses a separate browser partition and a narrow preload bridge for presentation/navigation only. It has no Metaverse IPC API. Only the active runtime's authenticated URL can attach; guest navigations are restricted and external HTTPS links open in the system browser. Metaverse language, theme, font and size are forwarded to the guest; custom fonts use the existing read-only font protocol.

`plugin/client.js` composes the public slot/service APIs: original chat and session browser, model forms, presets, plugin manager and plugin-specific settings. Its source modules are bundled into one client script during runtime staging. Plugin settings use one searchable catalog for enabled and disabled plugins, with registered forms collected under plugin configuration. Cards reuse the original manager actions, installation dialogs and configuration/detail views through the pinned manager's shared navigation store. Core management dependencies and preset-owned entries retain their actual read-only state and explanation. The plugin hides branding, removes duplicate settings chrome, and adds a recoverable delete action. The `tool` command reads the current Tool Management catalog through a narrow guest-to-host bridge and stages the selected tool entry in the conversation composer. Runtime staging places it in the Add group of the pinned Harness command menu.

The sidebar imports ZIP files produced by Harness's Download Log command. The authenticated Host route checks the archive paths, size, session format and attachment digests, then restores the root session and subagent logs into the current workspace's session store. Identical existing sessions can be reopened; conflicting IDs are rejected. Import keeps the conversation events and attachments so the restored session can continue. ZIP input is limited to 100 MiB compressed and 300 MiB expanded. Upstream session logs remain local; optional upload/telemetry plugins are disabled by the generated profile overlay. The host plugin registers the current workspace and adds the existing platform tools to normal system-prompt assembly.

Checks: `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`. Runtime tests cover concurrent starts, isolation, cancellation, readiness timeouts, guest authorization and generated-file symlinks. For UI execution checks use a temporary workspace and a local mock model endpoint, so no real provider credentials or billable requests are required. Windows/Linux native execution requires verification on those systems; staging their package variants is not a substitute for OS smoke tests.
